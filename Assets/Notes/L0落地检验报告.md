### 5.2 潜在代码风险

| 风险点 | 位置 | 说明 |
|:---|:---|:---|
| `GridState.PlayerCard` 线性扫描 | `GridState.cs:30-42` | 每次访问 `PlayerCard` 遍历 `_cardsById.Values`。9 格场景无性能问题，但未来卡牌多了会成为瓶颈。建议缓存玩家卡引用。 |
| `GridState.AddCardToGrid` 不校验 Zone 重复 | `GridState.cs:129-154` | 将已在 Grid 上的卡 `AddCardToGrid` 到另一格时，会先 `RemoveFromCurrentCell`，但若卡同时在 `DungeonDeck` 中则不会处理。可能导致同一 CardInstance 在逻辑上存在于两个 Zone。 |
| `PlayerInteractAction` 的 `default` 分支 | `PlayerInteractAction.cs:53-55` | `switch` 的 `default` 分支对所有未明确处理的类型（Item、StatUpgrade、Chest、Food、Mentor、ShopProduct 等）直接 `RemoveCard`。这意味着若 AI 内容未正确处理这些类型，它们会无声消失。 |
| `DomainFacade.SubmitIntentAsync` 返回最后一个 Batch | `DomainFacade.cs:64-65` | 若一个意图触发多个 Action（未来可能），只返回最后一个 Batch，前面的事件会丢失在返回值中（但仍保存在 `Context.Batches` 中）。 |
| `CombatResolution.ApplyDamage` 对 `MaxHp <= 0` 的卡 | `CombatResolution.cs:19-46` | 若目标 `MaxHp == 0`（如金币卡），`ApplyHpLoss` 中 `Math.Max(0, amount)` 然后 `SetCurrentHp(CurrentHp - hpLoss)`。由于 `MaxHp <= 0` 时 `SetCurrentHp` 会将 `MaxHp` 设为 `Math.Max(0, value)`，这可能导致对非生物卡意外设置 HP。需要明确非生物卡不应走 `ApplyDamage`。 |

### 7.2 是否适合全面 L1 铺量开发？

**结论：不建议立即全面 L1 铺量。**

理由：
1. **内容无法呼吸**：没有 `OnRevealed`/`OnDestroyed`/`OnInteract` 回调，AI 写的任何怪物/机关/道具都是死代码。
2. **核心机制悬空**：好战、伏击、复仇、尖刺、弩箭、散子——这些设计文档中定义的**核心差异化机制**目前完全无法工作。
3. **伤害结算孤立**：刺皮、庇佑、破甲、历战等机制因为没有 Hook 接入点而无法介入战斗。
4. **没有房间可进**：DungeonDeckBuilder、GridDealer、MonsterAllocationRule 完全空白，无法生成任何战斗房。
5. **存档断档**：战斗房内不能保存，这意味着玩家任何进度在退出游戏后都会丢失。

### 7.3 建议的最小前置工作（约 1~2 周）

在进入 L1 全面内容铺量之前，建议先完成以下 **"神经系统接通"** 工作：

**Week 1: 内容回调 + Hook 接入**
1. `CardModel` 新增 `CanInteractWithPlayer` / `OnPlayerInteractAsync` 虚方法
2. `CardModel` 新增 `OnRevealedAsync` / `OnDestroyedAsync` 虚方法
3. `PlayerInteractAction` 改为虚方法分派（而非硬编码 switch）
4. `PlayerMoveAction` / `PlayerInteractAction` 末尾触发 `AfterPlayerActionCommitted`
5. `GridState.RevealAround` 和 `GridState.RemoveCard` 的翻牌逻辑后，触发 `OnRevealedAsync`
6. `CombatResolution.ApplyDamage` 接入 `Hook.Before/AfterDamageApplied`
7. 先攻机制实现（`CombatResolution.ResolvePlayerVsMonster` 中判断先攻）
8. 玩家死亡检测（`PlayerInteractAction` 中检查玩家是否死亡）

**Week 2: 房间生成 + 存档扩展**
1. 新建 `DungeonMapGenerator`（每层 9 节点）
2. 扩展 `RoomFactory`（餐厅、金币房、宝箱房、属性房、奖励房）
3. 实现 `DungeonDeckBuilder`
4. 实现 `MonsterAllocationRule`
5. 实现 `GridDealer`（含 `MinimumCoveragePolicy`）
6. 扩展存档 DTO（`CardInstanceDto`、`GridStateDto`、`RoomDomainStateDto`）
7. 补全 P0 测试到 18 项

完成以上工作后，地基牢固度可提升到 **85% 以上**，此时再启动 L1 内容铺量，AI 新增的内容将能够：**被正确生成、正确互动、正确触发效果、正确保存读取**。

## 八、最终评语

> "L0 的地基是一个**结构精良但神经系统尚未接通**的框架。`GridState` 和 `DomainEventBatch` 已经为 AI 内容提供了安全的操作边界和可观测的状态变化，但内容类目前还无法'呼吸'——它们不能被翻开、不能被摧毁、不能被互动、不能介入伤害结算。这不是地基不牢，而是'水电未通'。建议在全面 L1 铺量前先接通'水电'（内容回调机制 + Hook 接入 + 房间生成管线），否则 AI 写的内容将大量变成无法触发的死代码。"
