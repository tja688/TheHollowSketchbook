# question_1：项目级领域基础设施顶层设计

> 目标：把当前“可多项目复用的地基”之上缺失的、专属于《深入地牢》的项目级领域基础设施落地成一套可实现、可测试、可被 AI 安全调用的架构蓝图。  
> 核心判断：你原来的三层范式方向正确，但当前已有代码更像“通用地基”。《深入地牢》还需要一层“领域基础设施 / 领域抽象层”，它不是具体业务内容，也不是表现实现，而是把九宫格、卡牌、堆叠、翻面、互动、房间生成、词条触发这些游戏专属骨架固定下来。

---

## 0. 一句话结论

当前项目应该从“三层分离”升级为更清晰的“四层协作”：

```text
┌──────────────────────────────────────────────┐
│ 表现层 Presentation                           │
│ 人类绝对控制：UI、动画、音效、特效、镜头、输入反馈 │
├──────────────────────────────────────────────┤
│ 业务逻辑层 Game Logic / Content               │
│ AI 主导：具体卡牌、怪物、遗物、机关、道具、数值     │
├──────────────────────────────────────────────┤
│ 项目级领域基础设施 Domain Infrastructure        │  ← 本文重点
│ 人类设计框架，AI 只能调用或按契约扩展内容类         │
│ 九宫格、卡牌实例、堆叠、翻面、互动、房间生成管线     │
├──────────────────────────────────────────────┤
│ 通用基础设施 Foundation Infrastructure          │
│ 人类绝对控制：ModelDb、存档、RNG、ActionQueue、Hook │
└──────────────────────────────────────────────┘
```

**新增这一层的目的不是把业务逻辑拿回人类手里，而是给 AI 一套安全、稳定、统一的“游戏领域操作系统”。** 以后 AI 写“弩箭机关”“复仇骷髅”“法则魔杖”“勾绳”时，只能调用这些领域 API，不能自己到处操作格子、卡堆、表现对象和存档字段。

---

## 1. 为什么必须新增“项目级领域基础设施”

《深入地牢》的核心不是传统卡牌构筑，而是 **3×3 九宫格 + 翻牌 + 拖动 + 堆叠 + 互动 + 连锁触发**。这些不是某张卡的私有规则，而是所有规则共同依赖的“空间语法”。

例如：

- 玩家出生在格 8；
- 玩家正交相邻格的最上方卡牌会自动翻开；
- 玩家只能拖到空白格移动，或拖到正面朝上的卡牌互动；
- 互动时玩家位置不变；
- 卡牌被移除后，下方最上方卡牌自动翻开并立刻结算“被翻开时”效果；
- 每个战斗房间根据房间类型、层数和节点生成地城牌组，并按规则分布到九宫格；
- 道具卡不计入玩家行动，玩家移动和互动计入行动；
- 怪物词条、机关、遗物、道具都依赖“正交相邻”“同列上方”“堆叠顶部”“下一次玩家行动后”等空间/时序语义。

这些规则如果让 AI 在每个内容类中自己实现，会迅速出现三类问题：

1. **重复实现**：每个怪物、机关、道具都自己写一套“找相邻格”“移动卡牌”“翻开卡牌”。
2. **规则漂移**：有的地方认为“新翻开的好战怪物立刻响应本次行动”，有的地方认为“不响应”。
3. **边界侵蚀**：AI 为了让业务跑起来，开始直接改 GridCell、Creature、Presentation Controller、Save DTO，三层分离失效。

所以，这一层必须由人类先定框架，再让 AI 在框架内写内容。

## 2. 四层边界定义

| 层级 | 责任 | 示例 | 所有权 | AI 权限 |
|---|---|---|---|---|
| 通用基础设施 Foundation | 可跨卡牌类项目复用的底层能力 | `ModelDb`、`AbstractModel`、`DeterministicRng`、`SaveManager`、`ActionQueue`、基础 Hook、序列化 | 人类 | 只能调用，不能修改 |
| 项目级领域基础设施 Domain | 《深入地牢》专属的稳定游戏语法 | `GridState`、`GridCell`、`CardInstance`、`DungeonDeck`、`PlayerIntent`、`DamageInfo`、`RoomContentGenerator`、领域事件 | 人类主导 | 可以调用；新增 API 必须申请；可按模板新增内容子类 |
| 业务逻辑 Game Logic / Content | 具体内容和规则 | 骷髅、伏击、复仇、弩箭机关、传送机关、勾绳、无尽水袋、房间配置、数值 | AI 主导，人类审核 | 可写、可迭代，但不能越过 Domain API |
| 表现层 Presentation | 所有视觉、声音、手感、输入反馈 | 卡牌 prefab、翻牌动画、受击特效、UI 面板、音频、镜头、拖动高亮 | 人类 | AI 只能通过事件/表现契约触发，不能实现 |

### 2.1 关键边界判断

下面这些内容必须属于 **项目级领域基础设施**，不应该散落在业务逻辑层：

- 九宫格坐标与格位编号。
- 正交相邻、同列上方、路径靠近等空间查询。
- 卡牌实例 ID、卡牌所在区域、堆叠顺序、正反面状态。
- 卡牌移动、交换、覆盖、移除、翻开、批量洗回地城牌组。
- 玩家行动计数与“下一次行动后”触发语义。
- 伤害结算的通用管线。
- 道具使用不计行动、玩家移动/互动计行动的统一判定。
- 房间内容生成管线与发牌分布算法。
- 存档中卡牌、格子、堆叠、触发器、道具栏、遗物、词条状态的序列化格式。
- 面向表现层的领域事件流。

下面这些才属于 **业务逻辑层**：

- “弩箭机关摧毁后对同列上方所有翻开卡造成 6 点伤害”。
- “复仇骷髅每有一张怪物卡被移除攻击 +2”。
- “勾绳选择方向后把目标卡移动到相邻格”。
- “宝箱卡提供 3 个遗物选项，65/30/5 品质概率”。
- “村好剑击败精英或层主后攻击永久 +2”。
- “第 4~6 节点可选商店和精英战斗”。

## 4. 全局领域不变量

本层最重要的价值是提供不变量。AI 写内容时只允许调用 API，不能破坏这些不变量。

### 4.1 九宫格不变量

1. 九宫格固定为 3×3，共 9 个格子。
2. 格位编号使用设计文档的行优先顺序：格 1~格 9。
3. 内部坐标建议使用 0-based：`GridCoord(row, col)`，但必须提供 `CellIndex` 与 `FromCellIndex(1..9)`。
4. 玩家卡在一个房间初始化时默认出生于格 8。
5. 任意时刻正常战斗房内必须存在且仅存在一张玩家卡。
6. 每个格子持有一个有序卡堆，最后一个元素为最上方卡牌。
7. 普通互动只能针对格子的最上方卡牌。
8. 被覆盖到下方的卡牌默认重新变为正面朝下，除非某个领域 API 明确允许保留状态。
9. 卡牌不能同时存在于两个 Zone：Grid、DungeonDeck、Inventory、RelicInventory、Choice、Removed 只能择一。
10. 所有会改变格子、堆叠、翻面、Zone 的操作必须通过 `GridState` 或 Domain Operation 完成。

### 4.2 互动不变量

1. 玩家卡可拖动。
2. 玩家卡拖到空白格：移动，计为玩家行动。
3. 玩家卡拖到正面朝上的非玩家卡：互动，计为玩家行动。
4. 玩家卡互动时自身位置不变。
5. 道具卡相关行为不计为玩家行动，包括收入道具格、拖出、使用。
6. 玩家行动只在领域层统一提交，不能由表现层或某个内容类自己加计数。
7. “下一次玩家行动后”必须基于统一的 `PlayerActionCounter`，不能由每张卡自己维护一个本地计数器。

### 4.3 翻牌与连锁不变量

1. 玩家正交相邻格的最上方卡牌会自动翻开。
2. 只有最上方卡牌会被自动翻开。
3. 卡牌移除后，如果下方还有卡牌，则新的最上方卡牌自动翻开。
4. “被翻开时”效果在卡牌完成翻面后立即进入动作队列。
5. 新翻开的卡牌不应 retroactively 响应导致它翻开的那一次玩家行动。它从下一次玩家行动开始响应 `AfterPlayerActionCommitted`。
6. 如果翻开效果导致更多移除/翻开，必须通过动作队列按顺序结算。

### 4.4 确定性不变量

1. 所有随机数必须来自 `IRng` / `DeterministicRng`。
2. 业务逻辑层禁止使用 `System.Random`、`UnityEngine.Random`、`DateTime.Now`、帧时间作为规则随机源。
3. 所有同 seed、同输入意图序列必须产生同样的领域状态与领域事件序列。
4. 异步表现播放不能影响规则结果。

## 5. 核心模型设计

### 5.1 `GridCoord` 与 `GridDirection`

```csharp
public readonly record struct GridCoord(int Row, int Col)
{
    public bool IsValid => Row >= 0 && Row < 3 && Col >= 0 && Col < 3;
    public int CellIndex => Row * 3 + Col + 1; // 1..9

    public static GridCoord FromCellIndex(int index);
    public bool IsOrthogonalNeighborOf(GridCoord other);
    public int ManhattanDistanceTo(GridCoord other);
    public bool TryOffset(GridDirection direction, out GridCoord result);
}

public enum GridDirection
{
    Up,
    Down,
    Left,
    Right
}
```

`GridCoord` 必须是纯 C# 值对象，不引用 Unity 的 `Vector2Int`。表现层可以在适配层把 `GridCoord` 转成世界坐标。

建议提供查询工具：

```csharp
public static class GridQueries
{
    public static IReadOnlyList<GridCoord> OrthogonalNeighbors(GridCoord coord);
    public static IReadOnlyList<GridCoord> CoordsAboveSameColumn(GridCoord coord);
    public static IReadOnlyList<GridCoord> AllCoordsRowMajor();
    public static GridDirection? DirectionFromTo(GridCoord from, GridCoord to);
    public static GridCoord StepToward(GridCoord from, GridCoord target, GridState grid, MovementPolicy policy);
}
```

其中 `CoordsAboveSameColumn` 可直接服务弩箭机关，“正交相邻”服务视野、尖刺、伏击、散子、照明卡。

### 5.2 `CardModel` 与 `CardInstance`

推荐不要把“运行时位置、正反面、血量”等状态放进 `CardModel`。`CardModel` 是内容原型，`CardInstance` 是房间内的运行时实例。

```csharp
public abstract class CardModel : AbstractModel
{
    public abstract CardType CardType { get; }
    public abstract string TitleKey { get; }
    public abstract string DescriptionKey { get; }

    public virtual bool CanBeFaceDown => true;
    public virtual bool CanBeStoredInInventory => false;
    public virtual bool BlocksAutoReveal => false;

    public virtual CardInstance CreateInstance(CardInstanceId id, DomainContext ctx)
    {
        return new CardInstance(id, Id, CardType);
    }
}

public enum CardType
{
    Player,
    Monster,
    Trap,
    Item,
    Gold,
    StatUpgrade,
    Chest,
    Food,
    Mentor,
    ShopProduct,
    RouteChoice,
    Special
}
```

`CardInstance` 只负责“这张牌当前在哪里、是什么状态、有哪些运行时组件”。

```csharp
public sealed class CardInstance
{
    public CardInstanceId InstanceId { get; }
    public ModelId ModelId { get; }
    public CardType CardType { get; }

    public CardZone Zone { get; internal set; }
    public GridCoord? Coord { get; internal set; }
    public int StackIndex { get; internal set; }
    public bool IsFaceUp { get; internal set; }
    public bool IsRemoved { get; internal set; }

    public Creature Creature { get; internal set; }       // 玩家/怪物可用
    public CardDurability Durability { get; internal set; } // 机关等可用
    public RuntimeStateBag State { get; }                 // 冷却、计数、临时标记
}
```

`RuntimeStateBag` 用于少量内容状态，例如：

- 传送机关是否已经触发；
- 尖刺机关的 `TriggerAfterActionIndex`；
- 暴力卡造成的“下一次与怪物互动后恢复”；
- 复仇骷髅累计攻击加成；
- 大骷髅老爷上一次血量阈值。

不要让 AI 随便往 `Creature` 或 `Player` 加字段。临时状态应使用明确命名的 `RuntimeStateKey` 或内容模型自己的 Typed State。

### 5.3 `CardZone`

```csharp
public enum CardZone
{
    None,
    DungeonDeck,
    Grid,
    PlayerInventory,
    RelicInventory,
    ChoicePool,
    RewardQueue,
    Removed
}
```

为什么需要 Zone：

- 传送机关会把九宫格上除玩家外的所有卡牌洗回地城牌组；
- 道具卡可以在九宫格与道具牌格之间流转；
- 宝箱卡会打开三选一遗物，这些候选遗物不在 Grid，也不在 RelicInventory，而是在 ChoicePool；
- 存档必须知道每个实例在哪里；
- 表现层要知道某张卡是场上实体、道具栏实体、候选项还是已移除对象。

### 5.4 `GridCell` 与 `GridState`

`GridCell` 应该尽量小，只做卡堆容器。外部不能直接拿到可变 List。

```csharp
public sealed class GridCell
{
    public GridCoord Coord { get; }
    public bool IsEmpty => Count == 0;
    public int Count { get; }
    public CardInstance TopCard { get; }
    public IReadOnlyList<CardInstance> StackView { get; }

    internal void PushTop(CardInstance card);
    internal CardInstance PopTop();
    internal void Remove(CardInstance card);
    internal void InsertAt(int index, CardInstance card);
}
```

`GridState` 是唯一对外暴露操作的入口。

```csharp
public sealed class GridState
{
    public GridCell GetCell(GridCoord coord);
    public CardInstance PlayerCard { get; }
    public IEnumerable<CardInstance> AllGridCards { get; }
    public IEnumerable<CardInstance> FaceUpCards { get; }
    public IEnumerable<CardInstance> MonsterCards { get; }

    public bool IsEmpty(GridCoord coord);
    public CardInstance GetTopCard(GridCoord coord);
    public IReadOnlyList<CardInstance> GetStack(GridCoord coord);

    public GridOperationResult MoveCardToEmptyCell(CardInstance card, GridCoord to);
    public GridOperationResult MoveTopCardToTop(CardInstance card, GridCoord to);
    public GridOperationResult SwapTopCards(CardInstance a, CardInstance b);
    public GridOperationResult CoverCellWithCard(CardInstance card, GridCoord coord, CoverPolicy policy);
    public GridOperationResult RemoveCard(CardInstance card, RemoveReason reason);
    public GridOperationResult FlipTopCard(GridCoord coord, FlipReason reason);
    public GridOperationResult FlipCard(CardInstance card, FlipReason reason);
    public GridOperationResult RevealAround(GridCoord center, RevealPolicy policy);
    public GridOperationResult ShuffleNonPlayerGridCardsIntoDeck(DungeonDeck deck, IRng rng);
    public GridOperationResult RedistributeDeck(DungeonDeck deck, GridCoord excludedCoord, DealPolicy policy, IRng rng);
}
```

所有操作返回 `GridOperationResult`，其中包含：

```csharp
public sealed class GridOperationResult
{
    public bool Succeeded { get; }
    public string FailureCode { get; }
    public IReadOnlyList<DomainEvent> Events { get; }
    public IReadOnlyList<GameAction> FollowUpActions { get; }
}
```

这样可以做到：

- 规则结果可测试；
- 表现层能通过事件知道发生了什么；
- 翻牌/移除/触发可以形成后续动作队列；
- AI 不能直接改底层数据，只能拿到结果。

### 5.5 `DungeonDeck`

```csharp
public sealed class DungeonDeck
{
    public IReadOnlyList<CardInstance> Cards { get; }
    public int Count { get; }

    public void AddToTop(CardInstance card);
    public void AddToBottom(CardInstance card);
    public void AddRange(IEnumerable<CardInstance> cards);
    public CardInstance DrawTop();
    public void Shuffle(IRng rng);
    public IReadOnlyList<CardInstance> RemoveAll(Predicate<CardInstance> predicate);
}
```

本游戏的地城牌组不是传统 deckbuilder 的抽牌堆，而是“当前房间尚未或重新待分布的卡牌池”。它服务于：

- 房间初始化发牌；
- 传送机关洗回再分布；
- 未来可能的召唤、增援、事件牌重排。

### 5.6 玩家状态与属性系统

当前 `Player` 过于精简。建议新增 `PlayerRunState` 或扩展 `Player`，但保持 `Creature` 纯粹。

```csharp
public sealed class PlayerRunState
{
    public CharacterModel Character { get; }
    public Creature Creature { get; }
    public int Gold { get; private set; }

    public PlayerStats BaseStats { get; }
    public PlayerStats PermanentRunBonus { get; }
    public PlayerStats RoomTemporaryBonus { get; }

    public TraitInventory Traits { get; }

    public int GetDefense(StatQueryContext ctx);
```

建议把属性拆成四层：

| 来源 | 生命周期 | 示例 |

| 角色基础属性 | 开局固定 | 兵大哥：血量 8、攻击 3、防御 1 |

### 7.2 玩家移动动作

玩家拖到空白格：

```text
Submit MovePlayerIntent
  → PlayerMoveAction
    1. 校验目标为空格
    2. 移动玩家卡
    3. 计入玩家行动
    4. 触发 AfterPlayerActionCommitted
    5. 翻开玩家相邻格最上方卡牌
    6. 结算被翻开时效果
    7. 检查房间清场/失败
```

注意：如果第 5 步翻开了“好战”怪物，它不响应本次行动，从下一次玩家行动开始计数。

### 7.3 玩家互动动作

玩家拖到正面朝上的卡牌：

```text
Submit InteractWithCardIntent
  → PlayerInteractAction
    1. 校验目标是最上方正面卡牌
    2. 根据目标类型分派互动管线
       - Monster：战斗互动
       - Trap：摧毁/互伤互动
       - Chest：打开选择
       - Gold：获得金币
       - StatUpgrade：打开属性选择
       - Food：治疗
       - Mentor：获得技能词条并移除其他导师
       - ShopProduct：扣钱并获得商品
    3. 计入玩家行动
    4. 触发 AfterPlayerActionCommitted
    5. 处理死亡/移除/翻开连锁
    6. 检查房间清场/失败
```

互动分派可以通过目标卡模型的虚方法实现：

```csharp
public abstract class CardModel : AbstractModel
{
    public virtual bool CanInteractWithPlayer(CardInteractionContext ctx) => false;
    public virtual Task OnPlayerInteractAsync(CardInteractionContext ctx) => Task.CompletedTask;
}
```

但互动流程的外层顺序必须由领域层统一控制，不能让某张卡自己决定“是否计入行动”“是否触发房间清场”。

## 8. 玩家行动计数与时序语义

### 8.1 `PlayerActionCounter`

```csharp
public sealed class PlayerActionCounter
{
    public int Value { get; private set; }
    public DomainEvent Increment(PlayerIntent sourceIntent);
}
```

只在以下动作成功提交后增加：

- 玩家移动到空白格；
- 玩家与正面朝上的卡牌互动。

以下不增加：

- 道具卡收入道具栏；
- 道具使用；
- 道具从道具栏拖出；
- 主动遗物使用；
- 选择奖励/路线/方向；
- 表现层预览或取消拖动。

### 8.2 “下一次玩家行动后”的标准实现

以尖刺机关为例：

```text
尖刺机关被翻开时：
  card.State["triggerAfterActionIndex"] = actionCounter.Value + 1
  card.State["hasTriggered"] = false

AfterPlayerActionCommitted：
  if !hasTriggered && actionCounter.Value >= triggerAfterActionIndex:
      对正交相邻卡牌造成 6 点伤害
      hasTriggered = true
```

关键点：如果尖刺是在一次玩家移动后的自动揭示中翻开的，它不会在同一次玩家行动后立刻爆发，而是在下一次成功玩家行动后爆发。

### 8.3 “每三次行动”的标准实现

以好战为例：

```text
怪物翻开时：
  card.State["faceUpAtActionIndex"] = actionCounter.Value
  card.State["actionsSinceFaceUp"] = 0

AfterPlayerActionCommitted：
  if card.IsFaceUp && actionCounter.Value > faceUpAtActionIndex:
      actionsSinceFaceUp += 1
      if actionsSinceFaceUp % 3 == 0:
          向玩家靠近一格；若可互动则互动
```

这样可以避免“刚翻开的怪物吃到历史行动数”的歧义。

## 9. 伤害与战斗结算管线

### 9.1 泛化 `DamageInfo`

原来的 `CreatureCmd.DealDamage` 适合生物对生物，但《深入地牢》有机关、道具、遗物、卡牌效果等非 Creature 来源。因此建议泛化：

```csharp
public sealed class DamageInfo
{
    public DamageSource Source { get; }
    public DamageTarget Target { get; }
    public int BaseAmount { get; }
    public DamageKind Kind { get; }
    public bool IgnoreDefense { get; }
    public bool CanBePrevented { get; }
    public bool CanTriggerThorns { get; }
    public string Reason { get; }
}

public abstract record DamageSource;
public sealed record CreatureDamageSource(Creature Creature) : DamageSource;
public sealed record CardDamageSource(CardInstanceId Card) : DamageSource;
public sealed record ItemDamageSource(ModelId ItemId) : DamageSource;
public sealed record RelicDamageSource(ModelId RelicId) : DamageSource;
public sealed record EnvironmentDamageSource(string Id) : DamageSource;

public abstract record DamageTarget;
public sealed record CreatureDamageTarget(Creature Creature) : DamageTarget;
public sealed record CardDamageTarget(CardInstanceId Card) : DamageTarget;
```

### 9.2 玩家 vs 怪物

默认互动公式：

```text
玩家对怪物伤害 = max(0, 玩家攻击 - 怪物防御)
怪物对玩家伤害 = max(0, 怪物攻击 - 玩家防御)
```

结算顺序：

1. 检查先攻类词条或 Hook。
2. 默认玩家先造成伤害。
3. 若先手伤害导致目标死亡，则死亡方不能反击。
4. 双方同时受到致命伤害时同时死亡。
5. 怪物死亡后移除怪物卡，并给玩家 10 金币。
6. 触发“怪物移除”“怪物死亡”“卡牌移除”相关 Hook。

### 9.3 玩家 vs 机关

机关不是普通怪物，但有血量和可能的防御。建议使用 `CardDurability`：

```csharp
public sealed class CardDurability
{
    public int CurrentHp { get; private set; }
    public int MaxHp { get; }
    public int Defense { get; }
}
```

玩家对机关：

```text
玩家对机关伤害 = max(0, 玩家攻击 - 机关防御)
```

机关对玩家：

```text
机关对玩家伤害 = 固定值，不受玩家防御减免
```

机关血量归零时触发 `OnDestroyedAsync`，由具体机关实现效果。

### 9.4 道具/遗物/机关造成伤害

所有非战斗互动伤害也必须走 `ApplyDamageAsync(DamageInfo)`，这样才能统一触发：

- 庇佑魔法卡免疫下一次伤害；
- 刺皮反伤；
- 受击表现；
- 死亡/移除；
- 存档和回放日志。

## 10. Hook / Trait / Relic / Item 机制

### 10.1 事件通知与规则 Hook 分离

建议区分两套东西：

1. **DomainEvent**：已经发生的事实，主要给表现层、日志、调试器使用。
2. **Rule Hook**：规则结算中的可介入点，给词条、遗物、怪物能力使用。

不要让表现层事件反过来改变规则。规则变更必须在 Hook 或 Action 中完成。

### 10.2 推荐 Hook 点

```csharp
public abstract class TraitModel : AbstractModel
{
    public virtual int ModifyAttack(StatQueryContext ctx, int current) => current;
    public virtual int ModifyDefense(StatQueryContext ctx, int current) => current;
    public virtual int ModifyDamageDealt(DamageContext ctx, int current) => current;
    public virtual int ModifyDamageTaken(DamageContext ctx, int current) => current;

    public virtual Task OnCardFlippedAsync(CardFlippedContext ctx) => Task.CompletedTask;
    public virtual Task OnPlayerActionCommittedAsync(PlayerActionContext ctx) => Task.CompletedTask;
    public virtual Task OnCardRemovedAsync(CardRemovedContext ctx) => Task.CompletedTask;
    public virtual Task OnBeforeDamageAsync(DamageContext ctx) => Task.CompletedTask;
    public virtual Task OnAfterDamageAsync(DamageContext ctx, DamageResult result) => Task.CompletedTask;
    public virtual Task OnRoomEnteredAsync(RoomContext ctx) => Task.CompletedTask;
    public virtual Task OnRoomClearedAsync(RoomContext ctx) => Task.CompletedTask;
    public virtual Task OnEliteOrBossDefeatedAsync(RoomContext ctx) => Task.CompletedTask;
}
```

`RelicModel` 可以复用相同思想：

```csharp
public abstract class RelicModel : AbstractModel
{
    public abstract RelicRarity Rarity { get; }
    public abstract RelicKind Kind { get; } // Passive / Active / Initial

    public virtual int AttackBonus => 0;
    public virtual int DefenseBonus => 0;
    public virtual int MaxHpBonus => 0;

    public virtual bool CanActivate(ActiveRelicContext ctx) => false;
    public virtual Task ActivateAsync(ActiveRelicContext ctx) => Task.CompletedTask;

    public virtual Task OnRoomEnteredAsync(RoomContext ctx) => Task.CompletedTask;
    public virtual Task OnRoomClearedAsync(RoomContext ctx) => Task.CompletedTask;
    public virtual Task OnEliteOrBossDefeatedAsync(RoomContext ctx) => Task.CompletedTask;
    public virtual Task OnDamageTakenAsync(DamageContext ctx, DamageResult result) => Task.CompletedTask;
}
```

### 10.3 Hook 执行顺序

必须固定顺序，避免 AI 内容之间出现不可复现差异。

推荐顺序：

1. 系统级规则 Hook。
2. 玩家技能词条 Hook，按获得顺序。
3. 玩家遗物 Hook，按获得顺序；主动遗物只在主动使用时触发。
4. 场上正面朝上的怪物/机关 Hook，按格位编号，再按堆叠顶部优先。
5. 当前被操作卡牌的自身 Hook。
6. 房间/节点级 Hook。

如果有同类修正冲突，应提供策略：

- 数值加法：按顺序累加。
- 乘法：先加法后乘法，或统一定义 `StatModifierOrder`。
- 替换/免疫：使用优先级字段。
- 同类技能词条不可叠加：获得时覆盖或取强者。

## 12. 房间流程与内容生成

### 12.1 Run / Layer / Node

建议新增 `RunProgressionState`：

```csharp
public sealed class RunProgressionState
{
    public int LayerIndex { get; }      // 1..3
    public int NodeIndex { get; }       // 1..9
    public RoomType CurrentRoomType { get; }
    public IReadOnlyList<RoomChoice> PendingChoices { get; }
}
```

每层 9 个节点：

- 第 1 个固定奖励房；
- 第 8 个固定餐厅；
- 第 9 个固定层主战斗；
- 第 1~3 节点胜利后可选金币房、宝箱房、属性房；
- 第 4~6 节点胜利后可选金币房、宝箱房、属性房、商店、精英战斗；
- 第 7 节点胜利后固定进入餐厅；
- 层主战斗结束后进入下一层或通关。

### 12.4 怪物分配算法

把节点怪物等级范围做成配置：

```csharp
public sealed class MonsterAllocationRule
{
    public int NodeIndex { get; }
    public IReadOnlyList<MonsterTierRange> Ranges { get; }
}

public sealed record MonsterTierRange(int Level, int Min, int Max);
```

算法：

```text
target = 9 + layerIndex
for each level range:
    count[level] = rng.NextInt(min, maxInclusive)
while sum(count) < target:
    从最高等级开始依次补足，直到总数等于 target
if sum(count) > target:
    从最低优先级或超额等级回退，保证等于 target
```

原设计中范围随机后理论上可能超过 `9 + X`，因此领域层必须定义“超额时如何处理”。建议采用：

1. 首先按范围随机；
2. 若不足，从最高等级补足；
3. 若超额，从最低等级开始扣减，但不低于该等级最小值；仍超额则从最高等级扣减；
4. 最终严格等于 `9 + X`。

这样比默默允许超额更利于平衡和测试。

## 16. 自动验证与测试

### 16.1 不变量验证器

```csharp

```

每次 Debug 构建中，Action 结束后跑一次轻量验证。重点检查：

- 是否只有一张玩家卡；
- 是否有卡牌重复出现在多个 Zone；
- GridCell 堆叠顺序与 CardInstance.StackIndex 是否一致；

- Removed 卡是否仍在 Grid；
- 玩家所在格是否存在玩家卡；
- 餐厅/战斗房发牌策略是否符合政策；
- 行动计数是否只由合法动作增加；
- 所有随机操作是否来自 IRng。

### 16.2 P0 单元测试清单

必须先写测试，再让 AI 大规模填内容。

1. `GridCoord` 格位编号转换测试。
2. 正交相邻查询测试。
3. 玩家从格 8 移动到空格，行动计数 +1。
4. 玩家与怪物互动时位置不变。
5. 玩家相邻格自动翻开最上方卡。
6. 移除顶牌后下方卡自动翻开。
7. 翻开伏击者且玩家相邻时触发互动。
8. 尖刺机关翻开后下一次玩家行动才触发。
9. 好战怪物每三次后靠近玩家。
10. 弩箭机关只伤害同列上方翻开的卡。
11. 传送机关洗回、移动玩家、重新分布，且不把卡发到玩家所在格。
12. 勾绳移动任意卡到相邻格。
13. 翻转卡交换正面非玩家卡与背面卡的最上方卡。
14. 餐厅发牌不要求铺满 8 个非玩家格。
15. 战斗房发牌保证非玩家格至少一张。
16. 怪物分配算法严格等于 `9 + X`。
17. 同 seed + 同输入意图序列产生相同事件日志。
18. 保存后读取，Grid、卡牌状态、RNG、行动计数一致。

## 20. 最终架构判断

你现在已有的“地基”非常有价值，尤其是 ModelDb、AbstractModel、确定性 RNG、ActionQueue、存档、事件驱动这些东西，确实适合作为多卡牌项目复用的底层设施。

但《深入地牢》不是“任何卡牌游戏”，它是一个强空间结构的九宫格翻牌游戏。**九宫格空间规则就是这个项目的语言本身。** 这套语言必须由人类先固定下来，成为 AI 写内容时的语法约束。

所以，推荐你把原来的“基础设施层”拆成：

1. **通用基础设施**：跨项目复用，人类绝对控制；
2. **项目级领域基础设施**：本项目专属，人类设计，AI 调用；
3. **业务逻辑层**：AI 大规模生产；
4. **表现层**：人类控制，通过事件和表现契约接入。

这不是推翻你的三层范式，而是把“基础设施”这个词拆得更准确。这样 AI 既有足够强的工具可用，又没有机会把核心架构写成屎山。
