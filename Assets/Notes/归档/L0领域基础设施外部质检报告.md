**正式结论：不建议判定“L0 全面落地完成”，不建议直接开放 L1 大规模内容铺量。**

当前代码已经具备一套可运行的九宫格 P0 骨架：格位、堆叠、基础移动、基础互动、基础伤害、玩家行动计数、部分生命周期回调、道具栏/遗物栏雏形、17 个 EditMode 测试均通过。

## 三、严重缺漏

### 1. 存档 Restore 被高估，实际未形成完整闭环

计划要求 `RoomDomainStateDto` 覆盖 `RoomType`、层数、节点、行动计数、Grid、`DungeonDeck`、所有卡牌实例、ActiveChoices、PendingTriggers 等字段，见 `项目级领域基础设施顶层设计.md:1324-1335`。计划还明确要求保存 RNG、玩家属性、遗物、技能词条、道具栏、全部卡牌 Zone、行动计数、未结算选择、延迟触发器、路线选择，见 `项目级领域基础设施顶层设计.md:1348-1361`。

实际 `RoomDomainStateSaveDto` 只有 `ActionCounterValue`、`PlayerGold`、`Grid`、`ItemInventory`、`RelicInventory`，见 `DomainSaveDto.cs:70-77`。它没有保存 DungeonDeck 顺序、房间类型、层数节点、RNG、选择窗口、延迟触发器、路线选择、玩家多层属性与词条。

更严重的是，`DomainSaveAdapter.Restore()` 会用 `domain.Grid = restoredGrid` 替换 Grid，见 `DomainSaveAdapter.cs:40-44`，但 `DomainActionContext` 构造时已经把旧 Grid 传给了 `CombatResolution`，见 `DomainActionContext.cs:21-26`。`Combat` 是只读属性，见 `DomainActionContext.cs:34`。因此 Restore 后 `domain.Grid` 与 `domain.Combat` 内部引用可能分裂，读档后再战斗存在打到旧 Grid 或查找目标失败的风险。

另外，Restore 只通过 `RestoreGrid()` 把格子内卡牌注册进 `GridState`，随后 `BuildCardLookup(domain.Grid)` 只能看到 `grid.AllKnownCards`，见 `DomainSaveAdapter.cs:49-65` 与 `GridState.cs:46-49`。如果道具栏、牌库、Choice、Removed 区域的卡不在 Grid 中，恢复时就可能丢失或无法放回库存。

质检结论：`ARCHITECTURE.md:700`、`ARCHITECTURE.md:744`、`ARCHITECTURE.md:843` 中“存档完整闭环/SaveVersion=3 支持 Grid/CardInstance/Inventory”的表述过度乐观。当前只能算 Grid 基础字段 round-trip 测试通过，不能算领域存档完整落地。

修复备注（2026-06-05）：已先修掉 Restore 闭环硬伤，并把当前已存在的 L0 运行态保存范围从“仅 Grid + 金币/行动/背包/遗物”扩到“房间类型、层/节点、RNG、DungeonDeck 顺序、Inventory 卡实例、ChoiceSession、路线待选项”。`DomainActionContext` 新增 `ReplaceGrid()`，`CombatResolution` 改为可同步切换 Grid，读档后不再持有旧 Grid 引用。`RestoreGrid()` 会先注册全部已序列化卡实例，再分别恢复 Grid / Deck / Inventory，避免非 Grid 区域卡牌在恢复时丢失。新增 EditMode 回归覆盖 Combat 引用切换、Deck/Inventory/Choice/Progression/RNG round-trip；验证：`dotnet test Game.Core.Tests.csproj --no-restore` 通过，`DomainP0Tests.cs` 当前 `[Test]` 数量 28。仍未落地：真实 `PendingTrigger` 结构、玩家多层属性/词条存档；本次不再宣称“领域存档完整闭环”。

### 2. 房间生成、地图流程、发牌管线未落地

设计要求每层 9 节点：第 1 个奖励房、第 8 个餐厅、第 9 个层主，第 1~3 节点与第 4~6 节点有不同可选房间池，见 `项目级领域基础设施顶层设计.md:1095-1103` 与桌面设计案 `每层流程.md:2-6`。

设计要求实现 `DungeonDeckBuilder`、`MonsterAllocationRule`、`GridDealer`，并规定普通战斗、金币房、宝箱房、属性房、奖励房、商店、精英、层主、餐厅的构成，见 `项目级领域基础设施顶层设计.md:1119-1216`。桌面设计案也明确房间类型和发牌规则，见 `第二版设计.md:64-90`。

实际代码仍保留 StS 风格 `StandardActMapGenerator`，按 `ColumnCount`、`MapLength` 生成 DAG，见 `StandardActMapGenerator.cs:22-49`。`RoomType` 只有 `Combat/Event/Treasure/RestSite/Shop/Boss`，缺金币房、属性房、奖励房、餐厅等，见 `RoomType.cs:3-10`。

质检结论：房间生成管线是当前最大功能缺口之一。没有它，就不能自动初始化“一个符合设计规则的小房间”，更不能支撑后续 L1 内容规模化测试。

修复备注（2026-06-05）：已补齐 L0 最小房间生成、牌组构建与发牌管线。新增 `DungeonMapGenerator` / `RoomPlan` / `RunProgressionState`、`DungeonDeckBuilder` / `MonsterAllocationRule`、`GridDealer` / `DealPolicy`；扩展 `RoomType` 与 `MapPointType` 覆盖金币房、宝箱房、属性房、奖励房、餐厅、精英战斗、层主战斗。新增 EditMode 覆盖 9 节点规则、怪物数量严格等于 `9 + layerIndex`、战斗房铺满非玩家格、餐厅 4 张卡例外。验证：`Game.Core.Tests` 21/21 passed，job id：`5bacf646c646423c9f3cb055010ede66`。

### 3. 意图系统不完整，无法承载多数道具与路线/选择

当前 `PlayerIntent` 只有 `MovePlayer`、`InteractWithCard`、`StoreItem`、`UseItem`、`ChooseOption`、`ActivateRelic`，见 `PlayerIntent.cs:8-17`。`UseItemIntent` 只有一个 `InventorySlot`，见 `PlayerIntent.cs:62-70`，没有目标卡、目标格、方向、双目标等参数。

但内容契约里 `ItemTargetMode` 已经列出 `GridCell`、`MonsterCard`、`CardThenDirection`、`TwoCards`、`AnyCardThenAnyCell`，见 `ContentContractModels.cs:12-22`。这说明契约知道道具需要目标选择，但意图层没有提供承载结构。

`ChooseOptionIntent` 当前在 `DomainFacade` 中只是创建 `ChoiceResolved` 事件，未校验 session，未管理 ChoiceSession，也未执行奖励、宝箱、导师、路线选择等效果，见 `DomainFacade.cs:62-71`。

质检结论：`L1开发AI快速执行手册.md:68-71` 将 `UseItemIntent(slot)`、`ChooseOptionIntent`、`ActivateRelicIntent` 当作 P0 可用 API，会误导 L1 AI。对于勾绳、飞刀、翻转卡、照明卡、法则魔杖、路线选择等需求，当前意图层不足，AI 很容易绕开 Domain API 直接改 GridState 或 CardInstance。

修复备注（2026-06-05）：已补齐 L0 最小目标化意图承载与 ChoiceSession 校验。`UseItemIntent` 现在可携带目标卡、目标格、方向、双卡、卡后格等 `ItemTargetSelection`，`IntentValidator` 会按 `ItemTargetMode` 校验目标存在、格位合法、目标牌在 Grid 顶层且已翻面、MonsterCard 类型等，并在 `IntentPreview` 中返回目标高亮。新增 `ChoiceSession` / `ChoiceSessionStore`，`DomainActionContext` 持有打开中的选择会话，`ChooseOptionIntent` 会校验 session 存在、选项范围和一次性 resolve，`DomainFacade` 不再对未知 session 直接发 `ChoiceResolved`。本次未内置具体奖励、宝箱、导师、路线效果执行器，仅先封住 L0 意图承载与会话状态缺口。新增 EditMode 覆盖目标化道具和 ChoiceSession resolve；验证：`Game.Core.Tests` 23/23 passed，job id：`4689594584ed4965bb940a4561f892f3`。

### 4. Trait 生命周期未完整接入，怪物词条体系不稳

`TraitModel` 定义了 `OnCardFlippedAsync`、`OnPlayerActionCommittedAsync`、`OnCardRemovedAsync`、伤害前后 Hook 与伤害修正，见 `ContentContractModels.cs:250-285`。

但 `DomainActionContext.ProcessLifecycleEventsAsync()` 对 `CardFlipped` 和 `CardRemoved` 只调用 `CardModel.OnRevealedAsync()` 与 `CardModel.OnDestroyedAsync()`，见 `DomainActionContext.cs:149-171`。行动后响应只调用卡牌模型的 `OnAfterPlayerActionCommittedAsync()`，见 `DomainActionContext.cs:125-146`。Trait 的翻开、移除、行动后回调没有同等接入。

伤害 Hook 部分确实会通过 `NotifyCardTraitHooksAsync()` 和 `ModifyDamageByCardTraits()` 处理怪物 Trait，见 `DomainActionContext.cs:232-253` 与 `DomainActionContext.cs:256-320`，但这只覆盖伤害相关，不覆盖伏击、好战、复仇、散子等大量生命周期型词条。

质检结论：`ARCHITECTURE.md:846` 已承认 `TraitModel` 仍待激活，但 `ARCHITECTURE.md:866-868` 又说内容类现在可以呼吸，怪物可以被翻开时触发伏击、好战/尖刺可行动后响应。这个说法只对“直接覆盖 CardModel/TrapCardModel 虚方法”的内容成立，不对计划中的 TraitModel 体系成立。

修复备注（2026-06-05）：已接入 `TraitModel` 的非伤害生命周期回调。`DomainActionContext` 现在在 `CardFlipped` 处理时按“`CardModel.OnRevealedAsync` 后 Trait `OnCardFlippedAsync`”、在 `CardRemoved` 处理时按“`CardModel.OnDestroyedAsync` 后 Trait `OnCardRemovedAsync`”、在行动后观察者处理时按“`CardModel.OnAfterPlayerActionCommittedAsync` 后 Trait `OnPlayerActionCommittedAsync`”的顺序分发。新增 EditMode 回归测试覆盖同一怪物 Trait 的翻开、行动后、移除三类回调。验证：`dotnet build Game.Core.Tests.csproj --no-restore` 通过，0 error / 0 warning；Unity batchmode EditMode 因当前项目已有 Unity Editor 实例打开而无法独占运行，未生成测试 job id。

### 5. 领域不变量封闭不足，有外部篡改破口

`GridState.Cells` 返回内部数组 `_cells` 的 `IReadOnlyList` 视图，见 `GridState.cs:25-28`。`GridCell.StackView` 返回内部 `List<CardInstance>`，见 `GridCell.cs:38-41`。`PlayerInventory.Items` 返回内部 `List<CardInstance>`，见 `Inventories.cs:58-61`。调用方虽然拿到的是只读接口，但可以向下转型成数组或 `List<T>` 后修改集合，绕开 `GridState` 或领域 Action。

`DomainInvariantValidator` 目前只接收 `GridState`，只检查玩家数量和 Grid 内 Zone/Coord/StackIndex/Removed，见 `DomainInvariantValidator.cs:27-79`。计划要求验证 RoomDomainState，包括跨 Zone 重复、发牌策略、行动计数来源、随机源等，见 `项目级领域基础设施顶层设计.md:1436-1457`。

质检结论：当前不变量验证器太窄，不能保护“卡牌不能同时存在于两个 Zone”“道具栏/牌库/Choice/Removed 与 Grid 互斥”等核心规则。对于后续 AI 内容开发，这是结构性隐患。

修复备注（2026-06-05）：已封闭本段指出的集合下转型篡改破口：`GridState.Cells`、`GridCell.StackView`、`PlayerInventory.Items` 以及同类风险的 `DungeonDeck.Cards` 均改为返回不可向下转型为内部数组/List 的只读包装视图。`DomainInvariantValidator` 新增面向当前运行态聚合 `DomainActionContext` 的验证入口，在保留 Grid 局部校验的基础上，增加 Grid / DungeonDeck / PlayerInventory / 已追踪 Removed 卡之间的 CardInstanceId 唯一归属、容器期望 Zone、Removed 标记与坐标残留检查，可捕获同一卡同时出现在 Grid 与 Inventory/Deck 等跨 Zone 重复。新增 EditMode 回归覆盖集合封闭与跨 Zone 重复检测；验证：`dotnet build Game.Core.Tests.csproj --no-restore` 通过，0 error / 0 warning。

### 6. ActionQueue / DomainFacade 缺并发与重入保护

`DomainFacade.SubmitIntentAsync()` 每次验证后直接 enqueue，然后调用 `_executor.ExecuteAllAsync()`，见 `DomainFacade.cs:34-86`。`ActionExecutor.IsRunning` 只赋值，不阻止重复执行，见 `ActionSystem.cs:139-155`。`ActionQueueSet` 是普通 `Queue<GameAction>`，见 `ActionSystem.cs:75-99`。

如果表现层双击、异步 Hook 中再次提交 Intent、或两个 `SubmitIntentAsync()` 并发发生，可能出现多个 executor 同时 drain 同一队列、两个 Intent 都基于旧状态通过验证、事件批次顺序错乱等问题。

质检结论：L0 作为“AI 安全调用的领域操作系统”，需要明确定义 SubmitIntent 串行化策略。当前实现适合单线程测试，不足以作为强边界。

修复备注（2026-06-05）：已为 `DomainFacade.SubmitIntentAsync()` 加入单入口串行闸门，所有外部提交现在按调用顺序 await 同一条提交通道，不再并发验证/并发 drain。同次提交流中的 Hook/生命周期回调若重入调用 `SubmitIntentAsync()`，会被显式拒绝并返回 `IntentRejected(SubmitIntentReentrant)`，避免在旧状态快照上嵌套提交。`ActionExecutor.ExecuteAllAsync()` 也改为复用同一个运行中的 drain task，禁止重复启动多个 executor 同时消费同一队列。新增 EditMode 覆盖“并发双 Submit 串行执行”和“Hook 内重入提交被拒绝”；验证：`dotnet test Game.Core.Tests.csproj --no-restore` 通过，`DomainP0Tests.cs` 当前 `[Test]` 数量 26。

## 六、对 L1 开发手册的风险评估

`Assets/Notes/L1开发AI快速执行手册.md` 对后续 AI 的价值很高，但当前版本把若干未闭环能力写得过于确定：

| 手册表述 | 风险 |
|---|---|
| “存档完整 Restore 已落地，不再阻塞” | 与实际 DTO 缺字段、Combat 旧 Grid 引用、非 Grid 卡恢复风险不一致。 |
| “领域层会自动处理基础怪物/机关伤害、先攻、免疫、行动后回调、翻牌/移除连锁回调” | 对 CardModel 基类部分成立，对 TraitModel 和复杂机关/道具不成立。 |
| “UseItemIntent(slot)” | 不足以表达大多数设计道具的目标选择。 |
| “ChooseOptionIntent(sessionId, optionIndex)” | 当前只是发事件，没有 ChoiceSession 领域状态和效果执行。 |

建议在 L1 手册顶部增加红色状态声明：当前仅允许实现“不需要目标选择、不依赖房间生成、不依赖完整存档、不依赖 Trait 生命周期”的受控内容 Spike。正式铺量前必须补齐本报告 P0 修复项。

## 七、建议修复顺序

### P0：放行 L1 前必须修

1. 修复 `DomainSaveAdapter.Restore` 的引用一致性：Restore 后 `CombatResolution`、Validator、Deck、Inventory、Choice 必须指向同一份 RoomDomainState。
2. 扩展 `RoomDomainStateSaveDto`：至少覆盖 DungeonDeck、所有非 Grid 卡、RNG、房间类型/层数节点、ChoiceSession、PendingTrigger、主动遗物使用次数、路线选择。

4. 补齐目标化意图：`UseItemOnTargetIntent`、方向选择、双目标选择、`ChooseRouteIntent`、真实 `ChoiceSession`。
5. 接入 Trait 生命周期：翻开、移除、行动后响应必须能调用 `TraitModel`，并定义与 CardModel 虚方法的顺序。
6. 加串行化保护：`DomainFacade.SubmitIntentAsync` 必须明确拒绝、排队或 await 已运行 executor，避免并发 drain。
7. 扩展 `DomainInvariantValidator` 到 RoomDomainState，检查跨 Zone 重复、Deck/Inventory/Choice/Removed、行动计数来源、发牌策略。

5. 更新 `ARCHITECTURE.md` 和 `L1开发AI快速执行手册.md`，把“已完成”改成“基础可用/部分接通/待补齐”的真实状态。

## 九、最终判定

本次外部质检不认可“全面落地结束”的说法。

更准确的状态应写为：

```text
L0-P0 九宫格核心骨架：基础通过。
L0 项目级领域基础设施：部分落地，关键闭环未完成。
Foundation 通用基础设施：可复用但需补 Domain 桥接与并发安全。
L1 大规模内容开发：暂不建议放行。
```

如果当前必须推进后续开发，建议只允许小规模、受控内容 Spike，并严格限制在以下范围：不依赖房间生成、不依赖目标选择、不依赖完整存档、不依赖 Trait 生命周期、不修改存档/RNG/ActionQueue/ModelDb。正式 L1 铺量前，应先完成本报告 P0 修复项并补齐对应回归测试。
