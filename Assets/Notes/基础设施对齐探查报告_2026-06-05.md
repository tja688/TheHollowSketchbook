# 基础设施对齐探查报告（2026-06-05）

## 结论

当前 `Assets/Scripts/Game` 的 L0 领域基础设施不是空架子：3x3 网格、卡牌堆叠、顶牌互动、行动队列、领域事件、道具栏、遗物栏、房间牌组、9 节点层流程、领域存档和核心测试都已经落地。

## L1 前置风险

### 1. 战斗优先级与最新设计不完全一致

最新设计写明：无先攻时玩家先攻击，若目标未死亡才反击；双方都有先攻时仍是玩家先。见 `第二版设计.md:101-112`。

当前 `CombatResolution.ResolvePlayerVsMonsterAsync()` 对“双方都有先攻”和“双方都无先攻”走同一个 `else` 分支，先让玩家攻击，再无条件让怪物反击。见 `CombatResolution.cs:149-166`。现有测试 `CombatResolution_SimultaneousDeath_BothDie` 还把“双方都有先攻”解释为同时攻击，见 `DomainP0Tests.cs:227-249`。

风险：普通玩家攻击击杀怪物后，怪物仍可能反击；双方都有先攻时的规则与最新文档相反。这是 L1 内容前必须修的 P0 规则偏差。

建议：第一批修正战斗优先级测试和实现：无先攻与双方先攻都按玩家优先，只有目标未死亡才反击；单方先攻保留当前逻辑；若未来要支持真正同时伤害，应作为明确机制而不是默认先攻解释。

### 2. 道具使用仍允许计入玩家行动

最新设计写明：所有与道具卡相关的行为均不计玩家行动。见 `第二版设计.md:123-134`、`互动规则.md:9-12`。

当前 `ItemCardModel` 仍暴露 `CountsAsPlayerAction`，`UseItemAction` 会在该值为 true 时递增行动计数并通知行动后观察者。见 `ContentContractModels.cs:157-160`、`InventoryActions.cs:112-116`。现有测试还覆盖了可计行动道具，见 `DomainP0Tests.cs:403-427`。

风险：AI 写 L1 道具时可能误用旧契约，让尖刺机关、好战怪物等“行动后”触发规则漂移。

建议：第一批移除或封死 `CountsAsPlayerAction` 分支，更新测试与 `Architecture.md` 中“UseItemIntent 是否计行动”的描述。

### 3. 路线选择尚未按“棋盘上的可互动卡”建模

最新设计写明：清场后旧卡保留，路线选择以正面朝上的卡牌形式出现在棋盘上；玩家拖到对应卡进入下一房间。见 `第二版设计.md:89-97`。

当前已有 `CardType.RouteChoice`、`ChoiceSession`、`RouteChoicesGenerated` 事件和 `RunProgressionState.PendingChoices`，但 `PlayerIntent` 里没有 `ChooseRouteIntent`，也没有路线选择卡生成/挤位/进入下一房间动作。见 `PlayerIntent.cs:8-17`、`CardTypes.cs:50-63`、`RunProgressionState.cs:7-31`。

风险：L1 如果直接用 UI 菜单式选择，会绕过最新设计的棋盘空间规则；如果直接塞卡，又缺少统一进入房间动作和保存边界。

建议：第二批实现 `RouteChoiceCardModel` 或专用 `ChooseRouteIntent`。由于最新设计强调“拖玩家卡到路线卡”，更推荐把路线选择实现为 `RouteChoice` 卡互动，由 `PlayerInteractAction` 进入统一管线。

### 4. 内容层编译边界缺失

`Architecture.md` 已把 Content / Game Logic 定义为未来 L1 主要实现区，并明确建议新增 `Game.Content.asmdef`。见 `Architecture.md:20-29`、`Architecture.md:250-279`。

当前只有 `Game.Core.asmdef`、`Game.Core.Tests.asmdef`、`Game.Presentation.asmdef`，没有 `Assets/Scripts/Game/Content` 下的内容程序集。

风险：L1 内容可能误引用 Unity 表现层或直接访问 Presentation，破坏“内容只依赖 Core”的边界。

建议：第一批新增 `Assets/Scripts/Game/Content/Game.Content.asmdef`，引用 `Game.Core`，并启用 `noEngineReferences: true`。随后把 L1 内容注册、怪物、机关、道具、遗物、词条都放入 Content。

### 5. 牌组生成还在生产无法直接解析的临时 ModelId

`DungeonDeckBuilder` 当前用 `ModelId("l0", "monster-l" + tier + "-" + id)` 一类唯一 ID 创建卡牌。见 `DungeonDeckBuilder.cs:125-129`。但互动时 `DomainActionContext.ResolveCardModel()` 会从 `ModelDb` 按卡牌 `ModelId` 解析具体 `CardModel`。

风险：真实 L1 内容注册的是“骷髅”“带甲骷髅”“弩箭机关”等模型，不会注册每个运行时唯一 ID；房间发出的怪物、机关、道具卡可能在互动时 `CardModelNotFound`。

建议：第二批引入 `RoomContentCatalog` / `RoomContentGenerator`：牌组生成应抽取已注册的模型 ID，并通过模型创建或配置 `CardInstance`。运行时唯一性应只在 `CardInstanceId`，不应污染 `ModelId`。

### 6. 旧原型 Run 流与新 Domain 房间流并存

当前存在旧式 `RunManager`、`StandardActMapGenerator`、`RoomFactory`、`PrototypeRunController`，同时存在新式 `DungeonMapGenerator`、`RoomPlan`、`RunProgressionState`、`DungeonDeckBuilder`。`Architecture.md` 也指出 Presentation 仍是 skeleton。见 `RunManager.cs:11-184`、`PrototypeRunController.cs:15-19`、`Architecture.md:250-279`。

风险：L1 可能接到旧地图/房间系统，而非最新 3 层 × 9 节点、棋盘路线卡的 Domain 流。后续返工会很大。

建议：第二批定义一个明确的 `DomainRunFlow` 接入点：进入节点生成 `RoomPlan`，建立 `DomainActionContext`，调用 `DungeonDeckBuilder` 和 `GridDealer`，清场后生成路线卡，再保存于路线选择状态。旧 RunManager 保留为 prototype 或迁移外壳。

### 7. 玩家成长、词条、房间临时修正尚未一等建模

最新内容需要永久/本房间攻击、防御、生命、词条覆盖与不可叠加规则。见 `词条.md:1-24`、`遗物.md:10-64`、`房间衍生卡.md:9-13`。

当前玩家数值主要在 `CardInstance` 的 combat 字段和 runtime state 上，`Architecture.md` 也明确列出缺少 `PlayerRunState` / `StatModifier`。见 `Architecture.md:256-258`。

风险：遗物、导师、属性房、商店和临时 debuff 容易直接改卡牌字段，跨房间恢复、保存、覆盖规则会分裂。

建议：第三批在 Core 里实现轻量 `PlayerRunState` 和 `StatModifier`，至少支持永久基础值、本房间修正、词条集合、不可叠加/覆盖策略、进房/出房重置。

### 8. 延迟触发队列还不是可保存的一等对象

最新机关和词条需要“翻开后下一次玩家行动后”“每三次玩家行动”“血量跨越 10 的倍数”等时序触发。见 `机关卡.md:7-17`、`词条.md:10-16`。

当前可通过 `CardInstance.RuntimeState` 和生命周期 callback 表达部分逻辑，但 `Architecture.md` 明确说明还没有 first-class pending trigger queue。见 `Architecture.md:195`、`Architecture.md:258`。

风险：简单触发可以先写，但复杂延迟触发、保存恢复和队列顺序会依赖内容类自管，AI 编写内容时容易漂移。

建议：第三批决定是否引入 `PendingTriggerQueue`。若 L1 只做少量简单机关，可先用 runtime state；若 L1 直接做尖刺/传送/散子/好战全套，应先做可保存触发队列。

### 9. 怪物移除奖励不应只绑在玩家互动目标上

最新设计写明“每移除一张怪物卡，获得 10 金币”，精英和层主死亡还有额外奖励。见 `怪物设计.md:1-4`。

当前金币奖励在 `PlayerInteractAction.RemoveIfDead()` 内处理，主要覆盖玩家互动结束后检查目标死亡。见 `PlayerInteractAction.cs:60-79`。通用 `CombatResolution.ApplyDamageAsync()` 只产出伤害结果，不负责移除与奖励。见 `CombatResolution.cs:27-99`。

风险：飞刀、机关、遗物、词条造成的怪物死亡若内容类没有手动调用统一移除/奖励管线，金币、房间清场、精英/层主额外奖励可能漏发。

建议：第二批或第三批新增统一 `CardDeathResolver` / `MonsterRemovedRewardPipeline`，所有伤害来源都走同一套死亡、移除、金币和额外奖励规则。

`DungeonDeckBuilder.CardFactory` 重写为 `CreateFromCatalogOrFallback()` 双路径：当 catalog 有注册模型时，通过 `ModelDb.Get<CardModel>(registeredId).CreateInstance()` 创建真实卡片实例（真实 ModelId、真实属性）；catalog 为空时回退到合成 `l0` ModelId + 硬编码属性。此方案解决了原方案中"每张卡片用唯一 ModelId"导致的运行时 ID 膨胀问题——运行时唯一性现在完全由 `CardInstanceId` 承担，`ModelId` 回归其"标识内容模板"的本职。

**3. 路线选择卡、路线卡生成与挤位策略 — 已完成**

新增 `RouteChoiceCardModel`（抽象基类）和 `GenericRouteChoiceModel`（通用实现）。路线选择复用现有 `InteractWithCardIntent`，无需新增 Intent 类型——`PlayerInteractAction` 检测到 `RouteChoiceCardModel` 后走独立分支，跳过战斗/死亡/生命周期流程，直接调用 `RoomTransitionService.EnterRoom()`。

新增 `RoomTransitionService`（`Domain/Rooms/RoomTransitionService.cs`），`GenerateAndPlaceRouteCards()` 根据当前节点类型决定路线选项，创建路线卡并放置在空格子上；当无空格子时执行挤位策略（`CoverCellWithCard`，将路线卡覆盖在已有卡片上方）。`IntentValidator` 增加路线选择校验：房间未清场时拒绝路线卡交互（返回 `RoomNotCleared`）。

**4. 旧 RunManager 与新 Domain 流关系 — 已明确**

新增 `DomainRunFlow`（`Domain/DomainRunFlow.cs`）作为新 Domain 管线的唯一入口，封装 `DungeonMapGenerator`、`DungeonDeckBuilder`、`GridDealer`、`RoomTransitionService`。`StartNewRun()` 创建初始房间（Node 1, Reward 类型），发牌并配置完整 `DomainActionContext`。旧 `RunManager` 保持不动，新代码通过 `DomainRunFlow` 接入，两者并存直至 Presentation 层完成迁移。详细说明见 `Assets/Notes/DomainRunFlow.md`。

**5. 清场→路线卡→进入下一房间流程 — 已打通**

`PlayerInteractAction` 和 `InventoryActions`（UseItemAction / ActivateRelicAction）在交互完成后检测 `RoomClearChecker.IsRoomCleared()`，清场时触发 `RoomTransitionService.GenerateAndPlaceRouteCards()` 生成路线卡。玩家选择路线卡后，`EnterRoom()` 保留玩家 HP/ATK/DEF，创建新 `GridState`，构建新 `DungeonDeck`，发牌，推进 `RunProgressionState`，发出 `RoomEntered` 事件。`DomainEventType` 新增 `RouteChoiceSelected` 和 `RoomTransitioned`。

**测试验证：** 42/42 通过（34 项原有 + 8 项新增），0 失败。新增测试覆盖：RoomContentCatalog 注册查询、DungeonDeckBuilder catalog/合成双路径、路线卡生成与挤位、IntentValidator 路线卡校验、RoomTransition 房间切换、DomainRunFlow 初始状态。

**已知问题与后续注意：**

1. **DomainFacade 路线卡 NRE：** 通过完整 `DomainFacade.ExecuteIntent()` 管线交互路线卡时，`EnterRoom()` 替换 Grid 后，后续生命周期处理（`NotifyAfterPlayerActionCommittedAsync`）在新 Grid 上运行，新 Grid 中的卡片使用未注册的 fallback ModelId，可能触发 NullReference。当前测试通过直接调用 `EnterRoom()` 绕过此路径。**建议批次 3 修复：在 `PlayerInteractAction` 的路线分支中提前 return，避免后续生命周期处理。**
2. **保存边界：** 当前 `DomainSaveAdapter` 按房间保存 Grid 状态，但路线卡生成后、玩家选择前的中间状态尚未单独保存。如果在此阶段退出，恢复后会回到清场后状态但路线卡可能丢失。**建议后续考虑将路线选择作为独立保存点。**
3. **玩家卡片 ModelId：** `DomainRunFlow.StartNewRun()` 中玩家卡使用传入的 `playerModelId`，但未在 `ModelDb` 中强制校验。如果 Presentation 层传入未注册的 ModelId，运行时会抛异常。**建议增加防御性校验。**
4. **Tier 信息承载：** 当前 `DungeonDeckBuilder` 通过 catalog category 字符串（`monster-1`、`monster-2`）区分怪物层级。如果后续层级增多或需要动态 tier，建议将 tier 信息结构化到 `MonsterAllocationRule` 或 `RoomContentCatalog` 的 API 中，避免字符串拼接散落。

## 推荐 L1 启动口径

不建议现在直接“广泛上 L1 内容”。建议先执行批次 1，再用一个很窄的 L1 vertical slice 验证：

1. 一个普通怪物。
2. 一个简单机关。
3. 一个非计行动道具。
4. 一个普通宝箱/属性房选择。
5. 一个路线选择卡进入下一房间。

这条竖切能同时验证 Content 边界、ModelDb 注册、DungeonDeckBuilder、GridDealer、DomainFacade、事件输出、保存边界和 Presentation 接入，不会一次性引入全部遗物/词条复杂度。
